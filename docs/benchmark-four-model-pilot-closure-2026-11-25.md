# 四模型先导的完整槽位去向：原 46 条与续批 34 条

原定 80 个先导槽位现已全部有实际去向：**79 条有效、1 条 invalid**。有效观察的业务结果为 **75 通过、4 失败**，完整适用合同为 **36 通过、8 失败、35 未知**。这些合计用于核对覆盖与账务；原执行和续批保持各自的顺序、条件内分母及统计结果。

首批结果见[原 46 条报告](benchmark-four-model-pilot-2026-11-25.md)。第 46 条已发送请求但没有完整终态或用量，经过一次任务自有处理器的人工终止后封存；该 invalid 和 unknown 用量继续保留。续批只执行原来从未开始的第 47–80 槽，未重发原 1–46 槽。

| 执行部分 | 本次计划 / 已封存 | 有效 / invalid | 业务通过 / 失败 | 完整合同通过 / 失败 / 未知 |

原执行的 canonical 报告仍以 80 为计划分母，并保留当时的 34 格未启动。续批是新的独立工作计划，逐项链接这 34 个原槽位。两个报告的计划数不能相加成 114 个独立科学样本，也不能用续批结果覆盖原计划的停止记录。

续批由四个单模型 scope 顺序执行，形成 12 / 8 / 6 / 8 的分组顺序。原 slot、pair、case、material、model、condition、seed 与原顺序映射全部保留；执行顺序已改变，因此不声称原 runner 无干预继续，也不把两次执行静默拼成一个完整随机顺序的估计。

四个 scope 均为 development 材料上的 `pilot / native_calibration`，各自保留 native 与 Broker 的实际配对。沿用原 shared16 材料绑定、冻结产品与运行时、模型路由/API、`thinkingLevel=medium`、单次 `maxTokens=4096`、`free` 政策及串行模型执行。新的单模型 scope 使用所选模型的实际环境捕获；已逐一核得同模型、同消费方式的初始上下文和请求合同与原捕获一致。

唯一完整合同失败来自 Grok 4.7 的 native no-skill 场景：业务发票计算通过，但 `legal-selection` 观察到了允许候选集合之外的选择。这项失败不被业务正确掩盖。16 个整体未知也没有改判通过或确认失败。合同逐项计数为 81 通过、1 失败、20 未知，其中 critical 合同为 62 通过、6 未知；合同检查次数不等于 episode 数。

四个 scope 的家族覆盖不同，分别使用其预先声明的本地权重；单模型分析不产生跨模型交互结论。不能平均四个 scope 或前后两批的置信区间，也不能根据这些小规模先导计数给模型排名或宣布产品采用。

## 与正式 native 的界限

首次正式 native 的样本、模型、权重、阈值与算法以此前明示的 closed40 检查点为先导截点，在确认材料生成前固定。原 41–46 与本续批全部作为截点外结果报告，不用其成绩调整正式设计。

先导封存后，required 诊断发现了 Broker 元数据尚未准备完成就捕获初始上下文的公共运行时竞态。修复通过现有 refresh 命令等待目录发布，见 [PR84](https://github.com/yoyooyooo/pi-context-broker/pull/84)。新 store 对比和正式 native 将在新的共同 apparatus 身份下运行；本报告中的旧运行时、expectation 和有效 admission 原件保持不变。这是后续条件身份的明确变化，不能把新旧条件混称为同一冻结运行时。

本先导不计入首次正式确认样本，也不取代已有 Own20 的两版本比较。最终确认是否通过、失败或 inconclusive，须以其独立正式结果为准。

# Library title reuse, first-use concurrency and ordinary Pi adoption

Two concrete product gaps have been repaired and delivered to Pro, Mini and imile-win. Controlled regressions establish that an explicit Library source no longer repeats a descriptor GET merely to obtain its title, and that a delayed first initializer can reuse valid state published by a peer. Fresh ordinary Pi checks verify the accepted installed pair on all three machines.

The targeted two-observation real-model comparison has **not run**. Capacity admission stopped before configuration or captures. This checkpoint establishes the product repairs, their controlled verification and ordinary-installation adoption; it does not establish an end-to-end latency or real-model quality improvement for the new pair. The accompanying [public summary](../benchmark/results/2026-11-27-library-title/summary.json) separates these evidence levels and records the original receipt identities.

## Product findings and repairs

The [previous smart-cache comparison](https://github.com/yoyooyooo/pi-context-broker/blob/0cb3019795336248553770d1368ccd563905b60a/docs/benchmark-smart-cache-2026-11-27.md) left foreground acquisition costs visible. Following the actual source path exposed a smaller removable cost: Library validation already read and validated the Skills database descriptor, but `explicitSource` fetched it again for the title.

[CLI PR42](https://github.com/yoyooyooo/notion-skills-cli/pull/42) reuses the title from that same validated observation. It introduces no cache across operations. A later operation still sees a renamed title, and a moved or invalid table still fails the original ownership and schema checks. In controlled requests, explicit source loading falls from **15 to 14** requests and a representative catalog route from **17 to 16**. The focused regression passes 36 tests and 203 assertions. This is one fewer GET per actual `explicitSource` call, not a guaranteed one-request reduction for every SDK operation or complete episode.

Acceptance CI also exposed a concurrent first-use failure. Process A could observe an absent state database, process B could publish a complete current snapshot, and A could then mistake the root marker for an incompatible state transition. The repair rechecks the database at that boundary and reuses the peer's valid winner through the existing header and schema checks. A deterministic real two-process counterexample fails on the old implementation; the repaired implementation preserves the peer's original snapshot without restaging. The 16 related tests, typecheck and changed-file formatting pass. Both repairs entered `next` in PR42; no experimental model result was needed to justify fixing these concrete defects.

### A measurement defect repaired during adoption

The first Mini D and first imile A encountered real Notion 429 responses. The SDK waited and recovered, but the reused daily classifier required every individual attempt to succeed. The original runs therefore remain failed; their unexecuted later phases are not invented after the fact.

PR111 adds a narrow recovery interpretation for the ordinary cache action: a zero-body database or data-source descriptor GET must have an observed 429 rate-limit reason and Retry-After, complete SDK operation evidence, a subsequent matching request, and independently observed backoff before **each** retry. A later success cannot conceal an earlier premature retry. Every failed and successful attempt remains counted. Default strict metadata verification, Library structure proofs and bundled doctor CLI gates retain their original requirements.

The old-source counterexample fails at the original success assertion; the repaired verification passes **68 tests**. Offline reinterpretation of the retained evidence issues **zero new HTTP or model requests**:

| Original failed phase | Retained SDK attempts | Retained doctor attempts | Retry-After | Independently observed wait |
|---|---:|---:|---:|---:|
| Mini D | 41 | 25 | 21 s | 21.395 s |
| imile A | 25 | 0 | 6 s | 6.258 s |

Original result hashes remain unchanged, and the default strict mode still rejects these originals. Mini's separate recovery run and imile's new run under the identified repaired verifier have their own identities. The offline interpretation alone did not complete imile's missing B phase; the subsequent fresh D/A/B run did.

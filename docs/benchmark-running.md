# Run a frozen Benchmark comparison

Benchmark uses the existing paired-environment controller for isolated builds and
run state. It adds public business cases, private grading, actual Pi SDK episodes,
and evidence analysis. Use the maintained runtime and an explicitly named frozen
build. The ordinary daily `next` verification gate remains separate.

## Daily product iteration

Start with the latest project narrative, then inspect both repositories and the
actual Mini installation. A completed historical ticket does not establish the
current product state. The [product adoption record](benchmark-product-adoption-2026-11-26.md)
links the concrete changes, separately frozen comparisons, evidence limits and
ordinary-profile delivery. Its original evidence packages remain immutable.

1. **Select the product and the question.** Fetch and compare `next` and
   `benchmark` in both isolated checkouts. Bring accepted shared changes into
   Benchmark; keep product and general engineering fixes on `next`. Name the
   exact commits, current product gap and smallest existing case that exercises
   it. Reuse an applicable corpus and its native-equivalent files. A complete
   historical matrix is not a prerequisite for a product fix.
2. **Freeze the actual subjects.** Use the existing paired build entry and reuse
   verified dependency caches. A formal model subject needs the current
   Benchmark runtime in its frozen source tree; a pure `next` package alone
   does not contain it. Compare the product/SDK bytes with the daily candidate
   instead of editing a frozen manifest. Refresh a retained read-only Library
   through `fixture.mjs refresh-readonly` when its current SDK proof is needed.
3. **Declare only the next decision.** Follow the
   [standing continuation contract](benchmark-standing-campaign.md) with the
   existing grant, history baseline and ledger. Freeze a new scientific template
   and attempt for changed product, model, material or runtime conditions. The
   maintained comparison entry accepts two environments, or two explicit pairs;
   one representative case does not require expanding to every corpus family.
   For a bare Native/Broker comparison, declare `pi_mode`, `sources` and
   `native_root` among the intended `allowed_changes`, as well as its actual
   tool/catalog/guidance differences. A declaration from a Broker/Broker
   comparison does not cover these mode differences. The protocol still checks
   the actual captured manifests; do not weaken that check after a refusal.
4. **Inspect before transport.** Run `configure` to capture actual Pi loading,
   tool ownership, source readiness and serialized input without a model call.
   Inspect the relevant difference. For a daily integration change, also check
   the ordinary profile: an isolated profile cannot reveal an extension that
   shadows a product tool in the user's installation.
5. **Run and decide.** Run the frozen plan through `run-standing`. Review the
   actual business output, critical resource and adoption contracts, tool trace,
   input usage, duration and recovery. A narrow positive contract can support a
   bounded product decision while an unproved absence remains unknown. State
   that boundary; do not turn an unknown into a pass or claim general efficiency
   from one pair.
6. **Route findings and close the loop.** Repair gaps that affect this
   measurement or decision in the Benchmark mainline, then repeat the affected
   checks. Record other worthwhile product improvements in separate Linear
   issues with evidence, expected user benefit and a bounded validation path;
   they do not automatically block the next measurement. Continue testing the
   accepted `next`, then absorb and recheck those product changes when accepted.
   Shared product and engineering changes go through `next`; Benchmark-specific
   changes stay on `benchmark`. Product runtime changes follow the normal Pro,
   Mini and imile-win delivery contract. A verifier-only change does not imply a
   new product installation. Publish Benchmark evidence separately, update the
   project record and retain the raw artifacts and accounting needed by the
   next iteration.
   Retire owned mutable source, dependency and cache copies when their last
   consumer finishes. Record precise dispositions and actual free space; moving
   a path to same-volume Trash does not reclaim capacity. An evidence-only
   manifest is not a promise that the original build remains runnable.

## Start from an existing bounded setup

Read the task's setup JSON, its purpose and total budget before running anything.
Use absolute paths. The setup names two environments, selected model routes,
public material, private controller storage, adapter evidence, and episode and
batch limits. It never contains credentials. A prepared Notion binding names a
task-owned library and verified native-equivalent bytes.

```sh
node benchmark/cli.mjs configure --setup /absolute/task/setup.json
node benchmark/cli.mjs run --plan /absolute/task/batch/plan.json --limit 2
node benchmark/cli.mjs status --root /absolute/task/batch
```

`configure` writes the frozen protocol inside `plan.json`; the standalone
`validate` command is optional when a separate protocol file is available.
Configuration captures the real maintained Pi SDK startup and final provider
serialization without sending a model request. Cases with identical startup
inputs may share this expectation. Each actual episode independently verifies
its public input bytes, loaded resources and first serialized request before
transport. An expectation mismatch stops before submitting the business task.

Broker admission first joins the existing catalog owner through
`/context-broker status`, then calls the public `notion_list({})` metadata tool
when a Notion source is configured. That tool waits for host metadata publication;
transport idleness alone does not establish publication. The preparation probe
does not force a remote refresh, adopt a Skill, or deliver its result to the model.
Its result and SDK/HTTP observations remain preparation evidence, separate from
business tool counts and provider calls. Roots/catalogs and the initial context
are captured after that boundary. Startup and first-payload idle waits follow
the run's declared bounded duration or unbounded policy and cancellation; they
have no additional five-second deadline. Cleanup keeps its bounded settlement.
Capture and execution must use the same credential injection for their named
environment variables so their projections undergo the same redaction. Capture still blocks
provider transport and business tool execution. Keep older expectations and
failed admissions, and create a new capture identity after a runtime change.

Catalog candidate handles are random within each product session. Both initial
context and final-request comparisons resolve them through the paired product's
actual branch reducer and the independently observed complete catalog. Only
verified card locations receive a stable comparison identity. Raw context,
branch bindings, catalogs and provider payloads retain the original handles;
unknown handles, misplaced handles and source, scope or owner drift still stop
admission. Conditions without catalog handles retain their context unchanged.

Cases with multiple turns, fixture events or frozen clarification responses also
require a completed build containing the current common turn runtime. Configuration
checks this before preparing any remote fixture; capture and execution check it
again before reading model credentials or dispatching. If it reports
`BENCHMARK_TURN_RUNTIME_BUILD_MISMATCH`, create a fresh build from the intended
source and use a new setup identity. Keep the failed setup and old build as
evidence. Editing a frozen manifest or reusing an older startup capture cannot
make the runtime compatible.

The example limit of two is a slice of the frozen batch, not an extra batch.
Run the same plan again to continue its remaining slots. Completed slots are
never silently repeated. Model retries are disabled in the initial policy.
This continuation applies to an operator slice, not a retained core-evidence
stop. A core stop remains in force on later invocations until an eligible,
verified analysis revision resolves it or a new protocol declares the repair.

Each live finite-campaign boundary freshly verifies the registration chain,
all authorized historical evidence and the current completed prefix. The latest
full history proof also reconstructs every ancestor's accounting prefix and
retains each ancestor's original-result requirements. The same boundary uses
that verified amendment immediately; no proof survives into the next reservation.
Dispatch repeats this check after acquiring the campaign lease.

The controller checks both the invocation wall-clock budget and the absolute
model window again after that proof, immediately before each exclusive pilot
reservation. The window includes its start and excludes its end. Expiration
closes the batch with `batch_budget_exhausted` or `model_window_closed` and
does not start another episode or consume another reservation. A requested
slice limit is an upper bound; use the recorded completed prefix and closure
reason when deciding whether an independently authorized continuation is possible.

## Review the result

```sh
node benchmark/cli.mjs query --root /absolute/task/batch --outcome unknown
node benchmark/cli.mjs journey --root /absolute/task/batch --run retained-run-id
node benchmark/cli.mjs analyze --root /absolute/task/batch --out /absolute/environment/reports/first
node benchmark/cli.mjs reanalysis --root /absolute/task/batch --out /absolute/environment/reports/reanalysis-1
```

`query` and `journey` expose a read-only `decision`: original overall outcome,
business result, individual critical/noncritical contracts, execution coverage
and source-readback coverage. Opaque tool IDs/names and evidence refs explain
source limitations. Missing legacy readback is `unavailable`, not an empty or
complete observation; corrupt retained evidence still fails verification.
`--outcome` filters the original overall grade. The view does not rewrite stored
journeys or normalized bundles and does not regrade. Use the current reporting
CLI for this added view; an older frozen controller keeps its original output.

`journey` also returns a top-level `turns` view of actual user turns. It joins
retained turn boundaries and request identities to every actual provider
attempt, including retries. Each row contains marginal and cumulative input,
output and cache observations, request/tool counts, peak input, and original
evidence refs. Unknown usage stays unknown with a separately named known
subtotal; unassigned attempts cannot establish a complete turn cost. The first
provider request is separate from the complete first user turn.

The elapsed prefix starts at the retained episode start, so it includes startup
and inter-turn gaps. User-turn duration starts at that turn's actual start.
These use the original event clocks; the end event includes workspace capture.
Do not combine their values with the slightly earlier runtime turn-settled
clock or capped analysis scores. SDK operations remain a separate list with
their recorded start context. That context is not causal attribution, and an
operation crossing a turn boundary must not be counted twice.

The view retains an original artifact grade for a user turn only when its
uniquely named output has matching graded bytes, readback content and that
turn's workspace hash. It does not invent a complete per-turn grade. Resource
and legal-selection contracts keep their original episode scope. For a new
reuse experiment, check the private oracle's explicit turn binding and complete
resource delivery by its first required turn; later turns may use normal
session history. Missing coverage remains unknown.

A report-only reanalysis needs no `register-reanalysis` or zero-limit `run`.

```sh
node benchmark/cli.mjs run --plan /absolute/task/batch/plan.json --analysis-revision /absolute/task/analysis-revision.json --limit 0

```

The replacement list contains `{ "run_id": "existing-run", "directory":
"/absolute/new/normalized" }` entries. Applying the revision with limit zero
makes no model calls. It records the source revision and adopts verified usage
for those same runs, each counted once. Later runs use the registered analysis
revision and continue the original remaining slots.

Every episode keeps its raw result, model attempts, usage, tool lineage,
independent output readback, grading result and deterministic journey. A known
business error remains a valid failure. Missing evidence remains unknown.
Unsupported capabilities are reported separately. Unknown usage stops batch
expansion because its actual cost cannot be reserved safely.

## Setup fields and limits

### Reusing a complete private corpus

For material prepared before `configure`, supply a frozen full corpus snapshot:

```json
{
  "corpus": {
    "seed": "declared-material-seed",
    "split": "development",
    "material_version": "2",
    "snapshot": {
      "path": "/absolute/task/private-material/full-corpus.json",
      "sha256": "SHA256_OF_THE_EXACT_FILE_BYTES"
    },
    "selections": [{ "caseId": "implicit-01-a", "candidateCount": 16 }]
  }
}
```

The file contains exactly `{ "publicCorpus": ..., "control": ... }`, including
the original private canaries, oracles and seal. Its path must identify a regular
file outside repository, configuration and subject build/run roots. The reader
checks the byte hash, complete corpus identities, and the declared `seed`,
`split` and `material_version` before writing the setup. An explicitly selected
diagnostic `generator` must match its provenance and existing split/version
limits. Loading does not open a confirmation seal.

`corpus.snapshot` and `materialization_binding_file` are mutually exclusive.
The latter still selects an actual verified shared physical materialization;
it is not a corpus-only input. Without a snapshot, existing generation or shared
material loading remains available. Regenerating a corpus with the same seed
preserves public material but creates a new private canary, so it cannot replace
the full corpus used for earlier slot preparation.

Early preparation and recovery call `readCorpusSnapshot(setup)`, then the existing
`prepareCases` and `prepareEpisodeFixtures` APIs with that same returned object
and final slot schedule. They do not run `configure` or register a campaign.
Final `configure` uses the same snapshot and verifies already prepared slots
against the complete public and private corpus. It freezes the reference in
`execution.corpus_snapshot`; changed bytes or a different full slot corpus fail
before reuse. Missing slot records retain the existing read-only reconciliation
boundary. No uncertain write is replayed.

### Owned episode material

Cases with declared turn events require `episode_fixtures` in the setup. This
explicit policy names the authorized synthetic Notion parent and any pinned
sources. `configure` prepares one owned initial fixture for every scheduled
condition/repeat, verifies material parity, and captures each slot with zero model
sends before freezing the plan. Read-only cases may share their proven material.
The physical entry, prompt, inventory and exact startup expectation are frozen
per writable slot; dispatch and reanalysis cannot materialize a replacement or
fall back to another case's expectation. The canonical sample identities and
denominators remain unchanged.

This automatic path supports `placement: "notion"`, including pinned source
members; it rejects local/mixed placements before remote work. An ambiguous
initial preparation is retained and re-entry only performs read-only reconciliation
against the same owned scope. See [turn bridge and fixture ownership](benchmark-turn-bridge.md#writable-fixtures-for-every-scheduled-slot)
for the setup shape, evidence binding and recovery boundary.

`episode_fixtures.authoring: "native-main-exact-resources"` opts native Notion
owners into complete public import with only `SKILL.md` as Native Markdown.
Auxiliary Markdown remains an exact resource. The policy is frozen in each
fixture plan and recipe; it accepts only one present immutable version without
relation or metadata overrides. Pinned Source bindings retain their existing
path. See [fixture file authority](fixture-authoring.md) for command, preflight
and recovery constraints. Omitting this field retains the original authoring
policy and never changes an existing fixture's authority.

For a catalog that also contains relation-bearing objects, select individual
eligible owners by their canonical Skill IDs:

```json
{
  "episode_fixtures": {
    "version": 1,
    "project_page_id": "owned-synthetic-parent-uuid",
    "authoring_by_skill": {
      "references-01-a-grant": "native-main-exact-resources"
    }
  }
}
```

The global `authoring` field and `authoring_by_skill` map are mutually exclusive.
The map must be nonempty and name Skills in the selected owned catalogs. Unknown
IDs, unknown policies and ineligible selected objects fail validation. Selection
is explicit; the controller does not inspect extensions and silently choose a
policy. Unselected objects retain their complete original recipe, including
relations and metadata. Each slot freezes only its matching map entries.
For direct shared-material planning, `planBenchmarkFixture` and
`buildFixtureRecipe` accept the same map as `authoringBySkill`; the immutable
fixture plan records it as `authoring_by_skill`.

### Models and budgets

The controller accepts model configuration, not a fixed model enumeration.
`models.source_file`, `provider`, `ids`, and `api_key_env` select declared routes
from an existing registry. The generated registry references an environment
variable; the secret is passed only to the task process. No global model file or
daily tool installation is changed.

Each model needs `adapter_evidence_file` from the actual maintained SDK's
controlled transport test, an explicit observation window and effective
parameters. Unobservable alias backends remain opaque. Fixed and automatic
single-variant conditions retain their exact response-identity checks. A declared
mixed-route condition may use its own production fallback; it does not authorize
a different route or an auxiliary model. Unverified prices remain unknown while
token and network counts remain available.

A mixed group is a separate condition with routing policy
`{ mode: "mixed-route", route, configuration_sha256, reported_model_ids }`.
Freeze the actual transitive group configuration and exact allowed response IDs.
The configuration hash binds the declared condition; it does not independently
prove the live gateway configuration, successful provider or applied reasoning
effort. Preserve gateway evidence and every attempt, including treatment-related
fallback. An explicitly allowed exact group echo is `requested_route_alias` and
cannot identify the concrete backend. Fixed-route and auto-route policies still
require one declared model variant.

`budget.episode` sets elapsed time, actual requests, input/output tokens, HTTP
attempts and retries. `budget.batch` sets their aggregate limits and concurrency.
The initial controller dispatches one subject at a time. Output request limits
and cumulative guards are enforced; prospective input estimation is a heuristic,
not a proof of exact provider tokenization. All actual usage is retained.

`decision` freezes the absolute quality policy and any noninferiority or
efficiency thresholds before model results. Small samples can yield an
inconclusive decision. Zero observed failures or all ties do not establish a
narrow noninferiority margin.

`allowed_changes` declares differences between environments. Code Mode `free`,
`off` and `required` are separate policy conditions. `free` activates Pi's `on`
mode; `off` leaves Code Mode inactive; `required` activates Pi's `only` mode.
In `only`, active direct tools remain callable inside Code Mode but their direct
declarations are hidden. Model-only tools such as `tool_search` remain declared.
This uses Pi's supported exposure policy and does not force a tool call when a
task needs none. The runtime records the actual declarations and calls; use
policy interactions rather than grouping episodes afterward according to whether
a model happened to call Code Mode.
Older captures that recorded `required` while constructing Pi with `mode: 'on'`
do not demonstrate this policy. Retain them under their actual runtime identity;
new required diagnostics need a newly frozen controller and capture.

## Visibility and public distribution

The subject receives business inputs and declared Skill material. Full controller
source, private oracle and prior experiment results stay outside its run tree;
the runtime projection contains only the allowlisted observer modules. Exact
input inventories, trace evidence and private canaries check this boundary.
This is a same-user filesystem arrangement, not an operating-system sandbox.

Private raw bundles may contain machine paths and task-owned remote identities.
Distribute a separately sanitized package and its transformation manifest.
Retain the originals for internal traceability. Public synthetic materials and
offline statistics do not imply that every corpus case was executed remotely.
